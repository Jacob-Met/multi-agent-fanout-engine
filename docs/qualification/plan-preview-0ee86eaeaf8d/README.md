## Source custody and semantics

[Candidate manifest](candidate-manifest.json) pins all15 files in the executed candidate. All11 non-README original files are byte-identical; the original README remains an exact prefix. Native Plan, Route, EffortRouter, dispatch, Ledger, package manifest and existing workflow are unchanged. [Source preservation](source-preservation.json) and [current source/claim](source-scope.json) retain that boundary.

The helper preserves already-constructed native Plan identity. The CLI uses native strict JSON parsing and Plan.from_dict normalization, while recording raw input hashes separately. Native readiness is Plan.ready_parts(()) only. It is not queued/stored dispatch eligibility; configured routes do not establish actual provider authorization or capacity. Every part's explicit route is validated, including dependency-blocked parts. Configured step-up is metadata only.

The consumer's audit and independent controls deny database connections, sockets, child launches and step-up actions while the real preview succeeds. The inherited nine unit methods retain their original in-memory Ledger/local adapter controls; they are separate from preview execution. Neither this packet nor those local controls claims external worker operation.

The strict file/part/report limits belong to the consumer and do not change core policy. A completed report is serialized before output. New-file publication retains no-clobber semantics; kernel-limited staging fails without a target or leftover stage. Stdout failure returns a clean error; an arbitrary broken stream can already have received a prefix. Cleanup after an actual publication is a separate boundary: the inspected source explicitly reports publication if cleanup fails, but that rare cleanup branch was not simulated.
