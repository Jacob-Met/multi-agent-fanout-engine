# ThinkPad saved Fanout readers

The user-owned command **hamon-fanout-read** is installed for **jacob on hamon-thinkpad**. It opens an explicitly selected existing local Fanout ledger and exposes four accepted readers: project discovery, project inspection, recorded history, and a self-contained HTML review. There is no default database and no live service address in this entry point.

## Use the installed command

These examples use the fictional sample produced during receiving. Its seven parts are authored examples, not estate task status.

~~~sh
hamon-fanout-read --help

db=/home/jacob/fanout-readers-20261013-c4c3dc26dd94/stage/authored-sample.sqlite
hamon-fanout-read projects --database "$db"
hamon-fanout-read inspect --database "$db" --project sample
hamon-fanout-read history --database "$db" --project sample
~~~

For your own work, replace the database value with the explicit existing ledger you intend to inspect, and use the exact project ID returned by projects. The wrapper delegates to the existing read-only CLI parsers without rewriting their options. Each subcommand also accepts --help. Inspect and history accept a new --output JSON path; history additionally supports an exact --part ID. Projects can export a new catalog JSON file.

The already-produced offline page is:

~~~text
/home/jacob/fanout-readers-20261013-c4c3dc26dd94/stage/sample-review.html
~~~

Open that file directly in a browser. It contains the recorded states, dependency readiness, part details, and a download of the exact inspection JSON. It has no JavaScript, automatic refresh, browser storage or network resources. This adoption verified its generated bytes and embedded JSON; it did not add a fresh browser visual course.

To produce another review, choose a destination that does not yet exist:

~~~sh
hamon-fanout-read review --database "$db" --project sample \
  --output /home/jacob/fanout-sample-review-new.html
~~~

Outputs are create-only. Existing files and the selected database/SQLite sidecar names are refused by the accepted source. Read-only refers to recorded ledger contents; SQLite may maintain read-side WAL bookkeeping. Ready means recorded prerequisites are complete, not that a worker is available or a dispatch reservation exists. Unknown outcomes remain unknown.

## Inspection, withdrawal and retained failures

This installer is pinned to this account, directory identities, source and one new version. It is a reviewed receiving record, not a general unattended installer. Repeating stage or activate is refused by existing version/alias/output paths. Its two independent source reviews happened before native writes.

For a deliberate withdrawal, the recorded installer exposes an identity-conditional operation:

~~~sh

  /home/jacob/fanout-readers-20261013-c4c3dc26dd94/install_readers.py withdraw
~~~

It removes only the alias whose full current identity matches the installation receipt and expected version target. It preserves the version, private venv and receiving files. A changed alias is refused. Withdrawal was source-reviewed and **not exercised**.

An interruption can leave an incomplete private version, an unrecorded alias, or a child requiring inspection. Timeouts kill and reap the direct child only; descendants are not tracked. Receipt-write failure is not proof that an operation had no effect: withdrawal may already have happened, and a post-creation activation failure can retain an alias if identity was not captured or changed. Inspect actual identities and the retained raw logs before choosing any recovery; do not rerun stage to obscure the first result.
