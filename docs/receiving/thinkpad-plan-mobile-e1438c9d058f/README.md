## Separate receiving phases

The helper's `stage`, `complete-stage`, `activate` and `withdraw` subcommands are consequential operations. They are not an instruction to execute every phase. Each is run only under its own reviewed concrete receiver/configuration. A new machine or changed input needs a new admission; editing these pins to force acceptance is not part of this recipe.

1. **Metadata admission.** The native record binds the old alias inode and target, canonical interpreter, 112 protected entries, 64 inherited inputs, sixteen roots with 1,145 entries, eight selected current records, fifteen typed links with referents and twenty old modules. It checks available persistent storage. No comparator baseline is repeated.
2. **Fresh inactive stage, when its destinations are absent.** Create only the fresh version and `stage-v2/` directory. This path is unavailable on the current device because the first attempt already created the version; it is not the continuation command. One setup child has a 60-second limit and a bounded three-second collection after termination. Then exactly four product children each have 15+3-second bounds: default comparison JSON; HTML to a new file; occupied HTML refusal; saved queued-route control. Expected statuses are `0, 0, 1, 0`. The corrected exact native JSON, HTML and 1,010-byte queued report are frozen before this revised recipe is authored. All raw streams and child facts are retained before acceptance checks.
3. **Remaining-two continuation on this device.** `complete-stage` requires the exact retained V1 config, failed outer receipt, read-only closure, all three successful process rows and full streams, all forty new-version entries and five typed links. It checks the original 112 protected entries (with alias separately guarded), 114 inputs and twenty root maps. It reads the existing 18,091-byte HTML against the corrected frozen oracle. It then runs only occupied-output refusal against that same file and the pending queued-route control, each with 15+3-second bounds, into `stage-v2/`. It does not recreate the environment, recopy modules, rerun the default comparison or export another fresh HTML page. `staged-v2-receipt.json` records the three retained observations and two new observations with their actual separate roots. The V1 failed receipt remains failed.
4. **Publication.** Receive the exact four recipe bodies and complete repository tree. Source publication does not switch the installed alias. The recipe bytes remain unchanged between stage and activation; observed outcomes are additive evidence.
5. **Guarded activation.** Recheck the exact old alias identity, complete accepted stage and new version, all nonalias state and inherited PATH. Atomically replace the alias with a link to the new wrapper. Make one actual inherited-PATH HTML export to `installed/comparison.html`, requiring all 18,091 bytes and the exact embedded JSON. The queued control uses the already admitted retained ledger, explicit routing file and project `fixture-handoff-51df5b72e832`. It emits advisory JSON only. ## Failure and recovery

Failures stop the current course. The helper saves raw output and process state, including initial timeout, kill error and secondary wait timeout where applicable. An unreaped or timed-out child prevents later product commands. There is no automatic retry, rollback or deletion of a partial version. The outer receiver has its own finite collection bound and records the actual alias and any exposed partial files.

If activation fails after the alias switch, do not assume the old target is active. Inspect `activation-failed.json`, the actual link and both phase/version records first. A separately reviewed `withdraw` operation requires the exact successful installation receipt and current alias identity, then restores the previous target using a new symlink inode. It retains the new version and all evidence. Withdrawal is unrun unless its own explicit receipt says otherwise; the helper is not a general emergency-recovery interface.

The full create-only publisher can report a post-publication staging-cleanup failure. Such a failure may leave a complete output file. Preserve the actual output and diagnostic rather than interpreting nonzero status as proof that nothing was written.

Keep the current compact installed handoff separate from earlier [PR118 receiving](https://github.com/Jacob-Met/multi-agent-fanout-engine/pull/118) and PR119 source/browser evidence. Link those earlier packets; do not recursively copy their full histories into this recipe.
